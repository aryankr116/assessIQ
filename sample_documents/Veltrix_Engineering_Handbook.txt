# Veltrix Systems Engineering and Operations Handbook

Veltrix Systems is a cloud software company that builds a unified commerce and logistics
platform used by mid-market retailers across North America, Europe, and Asia. Founded in 2014,
the company operates a multi-region SaaS product that processes payments, manages inventory,
orchestrates fulfilment, and provides analytics to roughly eleven thousand merchant accounts.
This handbook is the canonical reference for how engineering, security, data, and operations
teams design, build, deploy, and support the platform. It is intended for engineers, site
reliability engineers, data practitioners, product managers, and anyone who participates in the
on-call rotation. Every team is expected to keep its sections current, and any change to a
documented standard must go through the architecture review process described later in this
document.

The platform is organised as a set of loosely coupled services that communicate over well-
defined APIs and asynchronous event streams. Veltrix Systems favours small, autonomous teams
that own their services end to end, from design and implementation through deployment and
production support. This ownership model means the team that writes a service is also the team
that is paged when it misbehaves, which aligns incentives toward reliability and operability.
The remainder of this handbook codifies the practices that make that ownership model work at
scale.


## Mission, Vision, and Engineering Values

The mission of Veltrix Systems is to give independent retailers the same operational
sophistication as the largest global chains, without requiring them to employ large technical
teams. The engineering organisation supports that mission through a small number of durable
values that guide day-to-day decisions. These values are not slogans; they are tie-breakers
used when two reasonable approaches compete.

- Reliability is a feature. A capability that is not dependable is not shipped.
- Own what you build. The author of a change is accountable for its behaviour in production.
- Optimise for the reader. Code, documents, and runbooks are written for the next person.
- Make it observable. If you cannot measure a system, you cannot operate it.
- Prefer boring technology. Novelty must earn its keep against proven tools.
- Security and privacy are everyone's job, not a separate team's afterthought.
- Automate the repeatable. Human effort is reserved for judgement, not toil.


# Engineering Principles

These principles describe how engineers at the company reason about technical trade-offs. They
are intentionally opinionated. When a principle conflicts with a deadline, the conflict is
escalated to the team's engineering manager rather than silently resolved by cutting a corner
that the team will later regret.


## Simplicity and Boring Technology

The company deliberately prefers mature, widely understood technologies over newer
alternatives, even when the newer option is technically superior on paper. A mature technology
has known failure modes, abundant documentation, a large hiring pool, and battle-tested
operational tooling. When a team proposes adopting a new language, datastore, or framework, it
must document the specific capability gap that existing tools cannot fill, estimate the
operational cost of supporting the new technology for at least three years, and identify at
least two engineers who will own it. The default answer to a request for new infrastructure is
no, and the burden of proof rests with the proposer. This bias is not hostility to progress; it
is a recognition that every new component adds permanent operational surface area.


## Designing for Failure

Every networked system fails, and the platform is designed on the assumption that any
dependency can become slow or unavailable at any moment. Engineers are expected to apply
timeouts to every remote call, to bound retries with exponential backoff and jitter, and to use
circuit breakers so that a failing dependency does not exhaust the calling service's resources.
Bulkheads isolate pools of resources so that a problem in one code path cannot starve unrelated
work. Services degrade gracefully: when a non-essential dependency is unavailable, the service
continues to serve its core function with reduced capability rather than failing entirely. For
example, if the recommendation service is down, the storefront still renders the catalogue and
accepts orders; it simply omits personalised suggestions.


## Idempotency and Exactly-Once Semantics

Because the platform retries operations aggressively in the face of transient failures, every
mutating operation must be safe to execute more than once. Engineers achieve this with
idempotency keys: the client generates a unique key for an operation, and the server records
the key alongside the result so that a repeated request returns the original result rather than
performing the work twice. This is especially important for payments and inventory adjustments,
where duplicate processing would cause real financial harm. True exactly-once delivery is
impossible in a distributed system, so the platform implements effectively-once processing by
combining at-least-once delivery with idempotent consumers.


## Backward Compatibility and Evolution

Services evolve continuously, and the platform never takes a coordinated downtime window to
deploy. As a result, every change must be backward compatible with the versions still running.
Database schema changes follow an expand-contract pattern: first the schema is expanded to
support both the old and new shape, then code is migrated to use the new shape, and only after
every consumer has migrated is the old shape contracted away. API changes are additive; fields
are never removed or repurposed within a version. When a breaking change is unavoidable, a new
API version is introduced and the old version is supported until telemetry confirms that no
clients depend on it.


# Software Development Lifecycle

Work at the company flows through a lightweight but disciplined lifecycle that begins with a
problem statement and ends with a measured outcome in production. The goal of the process is
not ceremony; it is to ensure that the right problem is solved, that the solution is reviewed
by people who understand the blast radius, and that the change can be operated safely after it
ships.


## From Idea to Design Document

Any non-trivial change begins with a short design document, often called an RFC internally. The
document states the problem, the proposed solution, the alternatives considered, the impact on
existing systems, and the operational plan including metrics, alerts, and rollback strategy.
Design documents are circulated to the owning team and to any team whose systems are affected.
For changes that cross team boundaries or introduce new infrastructure, the document is brought
to the weekly architecture review forum, where senior engineers probe the design for failure
modes, security implications, and long-term maintenance cost. A design document is approved
when the reviewers are satisfied that the risks are understood and acceptable, not when the
design is perfect.


## Implementation and Code Review

Once a design is approved, implementation proceeds in small, reviewable increments. The company
strongly prefers many small pull requests over a single large one, because small changes are
easier to review carefully and safer to revert. Every change is submitted as a pull request and
must receive approval from at least one other engineer before it can be merged; changes to
sensitive systems such as payments, authentication, or data export require two approvals, at
least one of which must come from a designated owner of that system. Reviewers are expected to
check correctness, readability, test coverage, security implications, and operational impact,
and to be respectful and specific in their feedback.


## Release and Progressive Delivery

The platform ships continuously. Merged changes flow through an automated pipeline that builds
artefacts, runs the full test suite, and produces a deployable image. Deployments are
progressive: a new version is first released to an internal staging environment, then to a
small percentage of production traffic via a canary, and finally to the full fleet as
confidence grows. At each stage, automated checks compare error rates, latency, and saturation
against the previous version, and the rollout halts automatically if any guardrail metric
regresses. Feature flags decouple deployment from release, allowing code to be deployed dark
and enabled gradually for specific cohorts of merchants.


# Coding Standards

The company maintains language-specific coding standards to keep the codebase consistent and
approachable. Consistency reduces the cognitive cost of moving between services and makes
automated tooling more effective. The standards below are enforced by linters and formatters in
continuous integration; a change that violates them cannot be merged.


## Python Standard

All Python code targets Python 3.12. Formatting is handled by the Black formatter with a
100-character line limit and isort for imports, and code is linted with Ruff for linting and
mypy in strict mode for static type checking. Tests are written using pytest with fixtures, and
a minimum of eighty percent branch coverage on changed lines. Type hints are mandatory on all
public functions. Prefer dataclasses or Pydantic models over loose dictionaries. Use context
managers for any resource that must be released, and never catch a bare exception without re-
raising or logging it. These rules are checked automatically, and the build fails if any of
them is violated. When an exception to a rule is genuinely warranted, the engineer documents
the reason inline and obtains explicit approval from a code owner during review.


## TypeScript Standard

All TypeScript code targets TypeScript 5 in strict mode. Formatting is handled by Prettier with
two-space indentation, and code is linted with ESLint with the company shared configuration and
the no-floating-promises rule enabled. Tests are written using Vitest for unit tests and
Playwright for end-to-end browser tests. The any type is forbidden in application code. Model
API responses with explicit interfaces. Prefer immutable data and pure functions in business
logic, and keep side effects at the edges of the system. These rules are checked automatically,
and the build fails if any of them is violated. When an exception to a rule is genuinely
warranted, the engineer documents the reason inline and obtains explicit approval from a code
owner during review.


## Go Standard

All Go code targets the latest stable Go release. Formatting is handled by gofmt and goimports,
which are non-negotiable, and code is linted with golangci-lint with the company ruleset
including errcheck and staticcheck. Tests are written using the standard testing package with
table-driven tests and the race detector enabled in CI. Errors are values and must be handled
explicitly; never discard an error with the blank identifier. Use context for cancellation and
deadlines on every request path. Keep interfaces small and define them at the point of use.
These rules are checked automatically, and the build fails if any of them is violated. When an
exception to a rule is genuinely warranted, the engineer documents the reason inline and
obtains explicit approval from a code owner during review.


## Java Standard

All Java code targets Java 21 with records and pattern matching. Formatting is handled by the
Google Java Format, and code is linted with Error Prone and SpotBugs in the build. Tests are
written using JUnit 5 with AssertJ for fluent assertions and Testcontainers for integration
tests. Favour immutability with final fields and records. Avoid checked-exception-heavy
designs. Use constructor injection rather than field injection, and never perform blocking I/O
on a request-handling thread without a bounded pool. These rules are checked automatically, and
the build fails if any of them is violated. When an exception to a rule is genuinely warranted,
the engineer documents the reason inline and obtains explicit approval from a code owner during
review.


## SQL Standard

All SQL code targets PostgreSQL 15 dialect. Formatting is handled by uppercase keywords and one
clause per line, and code is linted with sqlfluff in continuous integration. Tests are written
using migration tests that apply and roll back every change against a disposable database.
Every query that runs in a request path must be backed by an index and reviewed with EXPLAIN
ANALYZE. Avoid SELECT star in application code. Write migrations that are reversible and that
never lock a large table for longer than a second. These rules are checked automatically, and
the build fails if any of them is violated. When an exception to a rule is genuinely warranted,
the engineer documents the reason inline and obtains explicit approval from a code owner during
review.


# Version Control and Branching

The company uses a trunk-based development model. Engineers integrate their work into the main
branch frequently, ideally several times a day, behind feature flags when a capability is not
yet ready for users. Long-lived feature branches are discouraged because they accumulate merge
conflicts and hide work from the rest of the team. Each pull request should represent a single
logical change with a clear description that explains not just what changed but why. Commit
messages follow the conventional commits format so that release notes and changelogs can be
generated automatically.

Branch protection rules require that the main branch always remains releasable. A change can be
merged only when it has the required approvals, all status checks are green, and the branch is
up to date with main. Force-pushing to protected branches is prohibited. When a defect is
discovered in production, the first response is to revert the offending change rather than to
roll forward with a fix, because a revert restores a known-good state quickly while a forward
fix carries fresh risk.


## Code Review Expectations

Code review is the primary mechanism by which the company maintains quality and spreads
knowledge. Reviewers are expected to respond to a review request within one business day,
because a blocked colleague is more expensive than a context switch. A good review checks that
the change is correct, that it is tested, that it is readable, that it handles errors and edge
cases, and that it does not introduce a security or privacy problem. Reviewers comment on the
code, not the author, and distinguish between blocking concerns and optional suggestions.
Authors, in turn, treat review comments as gifts rather than criticism and respond to each one,
either by making the change or by explaining why they chose not to.


# Testing Strategy

The company relies on an automated testing pyramid: a large base of fast unit tests, a smaller
layer of integration tests that exercise real dependencies, and a thin top layer of end-to-end
tests that validate critical user journeys. The shape of the pyramid matters because unit tests
are cheap and fast while end-to-end tests are slow and flaky; over-investing in the top of the
pyramid produces a suite that is expensive to run and unreliable, which erodes trust in the
tests themselves.

Unit tests verify the behaviour of a single unit of logic in isolation, using test doubles for
collaborators. They run in milliseconds and form the bulk of the suite. Integration tests
verify that a service works correctly against real dependencies such as a database or message
broker, using disposable containers that are created and destroyed for each run. End-to-end
tests exercise complete user journeys through the deployed system and are reserved for the
handful of flows whose failure would be catastrophic, such as checkout and login. The company
also invests in contract tests between services so that a provider cannot break a consumer
without the test suite catching it.

Beyond functional testing, the platform is validated with load tests that confirm each service
meets its latency and throughput targets under realistic traffic, and with chaos experiments
that deliberately inject failures such as instance termination, network latency, and dependency
outages to verify that the system degrades gracefully. Chaos experiments are run in a
controlled manner with a clear hypothesis, a blast radius limited by feature flags, and an
abort condition that stops the experiment if customer impact exceeds a threshold.


# Continuous Integration and Delivery

Every change passes through a continuous integration pipeline before it can be merged. The
pipeline checks out the code, restores cached dependencies, runs linters and formatters,
compiles the project, executes the unit and integration test suites, builds a container image,
scans that image for known vulnerabilities, and publishes the image to the artefact registry
with an immutable tag derived from the commit hash. The pipeline is designed to give feedback
quickly; the most common failures, such as linting and unit test errors, are reported within a
few minutes so that engineers are not left waiting.


## Deployment Strategy

Production deployments use a blue-green strategy combined with canary analysis. A new version,
the green fleet, is brought up alongside the current version, the blue fleet. A small fraction
of production traffic is routed to the green fleet, and an automated canary analysis compares
the green fleet's error rate, latency percentiles, and resource saturation against the blue
fleet over a fixed observation window. If the green fleet performs within the configured
tolerances, traffic is shifted to it gradually until it serves all requests, after which the
blue fleet is retired. If any guardrail metric regresses, the rollout halts and traffic is
returned to the blue fleet automatically. The specific guardrail is that an error rate above
two percent sustained over a five-minute window triggers an immediate automated rollback.


## Configuration and Secrets

Configuration is separated from code and supplied to services through environment variables and
a configuration service, so that the same artefact can be promoted unchanged from staging to
production. Secrets such as database passwords, API keys, and signing keys are never stored in
source control or baked into images. Instead they are stored in a dedicated secrets manager,
injected at runtime, and rotated automatically every ninety days. Access to secrets is governed
by role-based access control and every retrieval is logged for audit. A leaked secret is
treated as a security incident and the affected credential is rotated immediately.


# Cloud Infrastructure and Architecture

The platform runs on a major public cloud across three geographic regions, each of which
contains multiple isolated availability zones. Services are packaged as containers and
scheduled on a managed Kubernetes platform, which provides automated placement, self-healing,
and horizontal scaling. Infrastructure is defined as code and applied through the same review
and pipeline process as application code, so that the state of production is always
reproducible from a versioned repository. Manual changes to production infrastructure are
prohibited except during a declared incident, and any such change must be reconciled back into
code afterwards.

The architecture is multi-region and active-active for read traffic, with each region able to
serve customers independently. Write traffic for strongly consistent data is routed to a
primary region with synchronous replication to a standby, while eventually consistent data is
replicated asynchronously across all regions. A global traffic manager directs each customer to
the nearest healthy region and fails over automatically if a region becomes unhealthy. The
company's recovery objectives are a recovery time of fifteen minutes and a recovery point of
one minute for the most critical data domains, validated by regular disaster recovery
exercises.


# Service Catalogue

The platform comprises dozens of services. This catalogue documents the most important ones.
Each entry describes the service's purpose, the team that owns it, its technology stack, its
key dependencies, its service level objective, how it scales, its principal failure modes, and
the first steps an on-call engineer should take when it misbehaves. These entries are the
canonical source of truth and are kept current by the owning teams.


## Storefront API

The Storefront API is owned by the Channel team and is implemented in TypeScript on Node.js,
backed by PostgreSQL and Redis. It renders merchant storefronts and serves the catalogue and
product detail pages to shoppers. The service handles approximately 18,000 requests per minute
at peak and is governed by a service level objective of 99.95 percent availability and a 200
millisecond p99 latency, which the team monitors against an error budget and reviews in its
weekly operational review.

In terms of scaling, it scales horizontally behind a load balancer, and the autoscaler adds
replicas when cpu utilisation exceeds sixty percent or request latency rises. The team plans
capacity ahead of known demand peaks such as seasonal sales, and the service is load tested
regularly against traffic that exceeds its observed maximum so that headroom is verified rather
than assumed.

The service exposes a RESTful HTTP API with resources identified by stable URLs, cursor-based
pagination on collections, and machine-readable error codes. The Storefront API depends on the
Identity Service for authentication, consults the Configuration Service for feature flags, and
publishes domain events to the platform event bus where downstream consumers react
asynchronously. Its contracts are versioned and evolve additively so that consumers are never
broken by a change.

Its data model is normalised around its core aggregate, with foreign keys enforced in the
database and invariants protected inside transactions. All of its endpoints require
authentication, sensitive operations demand elevated authorisation, and every access is written
to the audit trail.

Its most common failure mode is database connection exhaustion under a traffic spike, which
manifests as rising latency followed by timeouts. The service exposes the four golden signals
of latency, traffic, errors, and saturation on a dashboard, and emits structured logs carrying
a correlation identifier on every request so that a single shopper journey can be traced across
services. Alerts are defined on customer-visible symptoms rather than on internal causes, so
the on-call engineer is paged when shoppers are actually affected.

On a page, the on-call engineer first checks the service dashboard for error rate and latency,
then inspects recent deployments, and rolls back if a deploy correlates with the regression. It
is covered by fast unit tests, integration tests against a disposable database, and contract
tests that prevent it from breaking its consumers. When the Storefront API is healthy and well
within its error budget, the Channel team is free to ship quickly; when the budget is under
pressure, the team pauses risky changes and prioritises reliability work until the budget
recovers.

Capacity for the Storefront API is planned from observed traffic plus a margin for growth and
bursts. At its peak of around 18,000 requests per minute the service runs comfortably below its
saturation point, and the autoscaler is configured to add capacity before latency degrades
rather than after. The team tracks the cost of running the service, attributes it to the
Channel team's budget, and reviews efficiency periodically, trimming over-provisioned resources
without eroding the headroom that protects the service level objective.

For resilience, the Storefront API runs as multiple replicas spread across availability zones
so that the loss of a single zone removes only a fraction of capacity. Its data is replicated
and backed up, and the backups are periodically restored in a drill to prove they work. In a
regional disaster the global traffic manager directs requests to a healthy region, where the
service serves from replicated data within the platform's recovery objectives. The team
participates in scheduled disaster-recovery exercises that deliberately fail components to
confirm the documented procedures actually hold.

The Storefront API's dependencies are documented explicitly so that the blast radius of any
outage is understood. It calls only the services it has been granted access to under the
default-deny network policy, applies a timeout and a circuit breaker to every remote call, and
degrades gracefully when a non-essential dependency is unavailable. Conversely, the team knows
which services depend on the Storefront API and treats its published API and events as a
contract that must not break, validating compatibility with contract tests before every
release.

# Data Engineering and the Data Platform

The data platform turns the raw events produced by operational services into trustworthy
datasets that power analytics, machine learning, and merchant-facing reports. Data flows from
services into a streaming backbone, lands in a raw zone of the data lake, and is then cleaned,
conformed, and modelled into curated tables in a warehouse. The platform follows a medallion
architecture with bronze, silver, and gold layers, where bronze holds raw immutable data,
silver holds cleaned and deduplicated data, and gold holds business-level aggregates ready for
consumption.

Data quality is enforced with automated tests that run as part of every pipeline: schema tests
confirm that columns have the expected types, freshness tests confirm that data has arrived
within its expected window, and volume tests confirm that row counts fall within expected
bounds. A pipeline that fails a quality test does not publish its output; instead it raises an
alert to the owning team and holds the previous good version in place so that downstream
consumers are never served corrupt data. Every dataset has a documented owner, a defined
service level for freshness, and lineage that traces each column back to its source.

# Databases and Storage

The company uses PostgreSQL as its default relational database because it is reliable, feature-
rich, and well understood by the engineering organisation. Each service owns its own database
and no service reaches directly into another service's tables; cross-service data access
happens through APIs and events. This discipline preserves the autonomy of teams and prevents
the tight coupling that a shared database inevitably produces. Where a workload genuinely needs
a different storage technology, such as full-text search or a cache, the team adopts a purpose-
built store and documents the operational implications.

Database access in request paths must be fast and bounded. Every query that runs in response to
a user request must be supported by an appropriate index, and engineers verify query plans with
the database's explain facility during development. Connection pools are sized deliberately and
protected so that a surge of traffic cannot open more connections than the database can serve.
Long-running analytical queries are never run against the primary operational database; they
run against replicas or the warehouse so that they cannot degrade the experience of shoppers.
Schema migrations are applied online using the expand-and-contract pattern so that they never
require downtime.


# Security and Compliance

Security is built into every layer of the platform rather than bolted on at the end. The
company practises defence in depth, layering controls so that the failure of any single control
does not lead to a breach. The security team sets standards, provides tooling, and reviews
high-risk changes, but the responsibility for building secure software rests with every
engineer. Threat modelling is part of the design process for any feature that handles sensitive
data or money, and the resulting risks are tracked to resolution.


## Authentication and Authorization

All access to customer data requires authentication, and sensitive operations additionally
require multi-factor authentication. The platform uses short-lived access tokens issued by the
Identity Service; tokens expire quickly and are refreshed through a secure flow, so that a
leaked token has a small window of usefulness. Authorization follows the principle of least
privilege and is enforced through role-based access control, where each role grants the minimum
permissions needed for a job function. Service-to-service calls are mutually authenticated, and
every authorization decision is logged so that access can be audited after the fact.


## Data Protection and Encryption

Data is encrypted in transit and at rest. All network communication uses transport encryption
with modern cipher suites, and certificates are rotated automatically. Data at rest in
databases, object storage, and backups is encrypted with keys managed by the cloud key
management service, and the keys themselves are rotated on a schedule. Particularly sensitive
fields, such as payment credentials, are tokenised so that the raw value never touches the
platform's databases; the company stores a token that references the value held by a compliant
payment processor, which keeps the bulk of the platform out of the scope of card-industry
compliance.


## Secure Development and Vulnerability Management

Security is verified continuously. Static analysis scans every change for common vulnerability
patterns, dependency scanning flags libraries with known vulnerabilities, and container images
are scanned before they can be deployed. Discovered vulnerabilities are triaged by severity,
and the company commits to remediating critical vulnerabilities within a tight deadline
measured in days. The company runs a responsible disclosure programme and engages external
testers for periodic penetration tests. Secrets are never committed to source control, and an
automated scanner blocks any commit that appears to contain a credential.


## Compliance and Privacy

The platform handles personal data and is therefore subject to privacy regulations including
the General Data Protection Regulation and equivalent regional laws. The company collects only
the data it needs, retains it only as long as necessary, and honours data subject rights
including access, correction, and deletion. Data processing activities are documented, data is
classified by sensitivity, and access to the most sensitive classifications is tightly
restricted and audited. The company undergoes annual external audits for its security
certifications and maintains a continuous control-monitoring programme so that compliance is a
steady-state property rather than an annual scramble.


# Observability

Operating the platform depends on the ability to understand its internal state from the
outside. The company instruments every service with three complementary signals: metrics, logs,
and traces. Metrics are numeric time series that answer how much and how fast; logs are
structured records of discrete events that answer what happened; and traces follow a single
request across service boundaries to answer where time was spent. Together these signals let an
engineer move from a high-level symptom to a specific root cause quickly.

Every service emits the four golden signals of latency, traffic, errors, and saturation, and
teams build dashboards that make the health of their service obvious at a glance. Logs are
structured as machine-readable records and carry a correlation identifier that ties together
all the work done on behalf of a single request, so that an engineer can reconstruct a
shopper's journey across a dozen services. Distributed tracing samples requests and records the
timing of each span, making it possible to see exactly which downstream call caused a latency
regression. Alerts are defined on symptoms that matter to customers rather than on causes, so
that the on-call engineer is paged when shoppers are affected, not every time a metric
twitches.


# Incident Management and On-Call

Despite every precaution, the platform sometimes fails, and the company treats incidents as a
normal part of operating a large system rather than as exceptional catastrophes. The goal of
incident management is to restore service quickly, to keep stakeholders informed, and to learn
enough to prevent a recurrence. Every engineer who owns a production service participates in an
on-call rotation, and the company invests in making on-call humane through good tooling,
accurate alerting, and a culture that does not punish people for being paged.


## Severity Levels and Roles

Incidents are classified by severity. A severity-one incident is a critical outage that
prevents shoppers from completing purchases or exposes data, and it mobilises the full incident
response process immediately at any hour. A severity-two incident causes significant
degradation but has a workaround or affects a subset of traffic. A severity-three incident is a
minor issue that can be handled during business hours. During a significant incident, clear
roles are assigned: an incident commander coordinates the response and makes decisions, a
communications lead keeps stakeholders informed, and subject-matter experts investigate and
apply fixes. Separating these roles keeps the response organised and prevents the commander
from disappearing into a debugging session.


## The Response and the Blameless Postmortem

The immediate priority during an incident is mitigation, not root cause. The responders restore
service by the fastest safe means, which is frequently a rollback, a traffic failover, or the
disabling of a feature flag, and only after the bleeding has stopped do they turn to
understanding why it happened. Every significant incident is followed by a blameless postmortem
that documents the timeline, the contributing factors, the impact, and a set of concrete action
items with owners and due dates. The postmortem is blameless because the company believes that
people act reasonably given the information and incentives available to them, and that durable
fixes come from improving systems rather than from blaming individuals.

shared cache is briefly unavailable. The incident was classified according to its customer
impact, communicated through the status page, and reviewed in the weekly operational review
where the action items were tracked to completion.


# Site Reliability Engineering and Service Levels

The company expresses its reliability commitments through service level objectives and manages
them with error budgets. A service level indicator is a quantitative measure of some aspect of
the service, such as the proportion of requests served successfully within a latency threshold.
A service level objective is a target for that indicator over a window, and the error budget is
the small amount of unreliability that the objective permits. When a service is comfortably
within its budget, teams are encouraged to ship quickly and take measured risks; when the
budget is exhausted, the team freezes risky changes and focuses on reliability until the budget
recovers.

Error budgets turn reliability from an argument into a number. Rather than debating whether the
platform is reliable enough, teams look at the budget and let it drive prioritisation. Toil,
the manual and repetitive operational work that scales with the size of the system, is measured
and deliberately reduced through automation, because a team buried in toil has no time to
improve reliability. The reliability organisation partners with product teams, embedding for a
time to improve a struggling service and then handing operational ownership back, rather than
permanently operating other teams' systems.


# API Design Guidelines

The platform's services communicate through APIs, and consistent API design makes the system
easier to understand and integrate. Public and internal HTTP APIs follow REST conventions:
resources are nouns identified by stable URLs, and the standard verbs express intent, with safe
methods for reads and idempotent methods for updates and deletes. Responses use standard status
codes, and errors carry a machine-readable code and a human-readable message so that clients
can both handle and display them. Collections are paginated with cursors rather than offsets so
that pagination remains stable as data changes.

APIs are versioned, and changes within a version are strictly additive so that existing clients
never break. New fields may be added, but fields are never removed or repurposed within a
version; a genuinely breaking change requires a new version that runs alongside the old one
until clients migrate. Every mutating endpoint accepts an idempotency key so that clients can
retry safely. APIs are rate-limited per client to protect the platform from misbehaving
integrations, and the limits are communicated through response headers so that well-behaved
clients can adapt. Webhooks are signed so that recipients can verify their authenticity, and
they are delivered with retries and a dead-letter path for endpoints that remain unavailable.


# Frontend Engineering

The merchant console and the shopper storefront are built as modern web applications. The
company values fast initial load and smooth interaction, and measures the experience with the
core web vitals that capture loading, interactivity, and visual stability. Applications are
server-rendered where it benefits performance and search visibility, and they hydrate into rich
client-side experiences. Components are built to be accessible by default, meeting recognised
accessibility standards so that the platform is usable by people with disabilities. State
management is kept simple, with server state handled by a data-fetching layer that caches and
revalidates, and local UI state kept close to the components that use it.

Performance is a budget that the frontend teams defend. Bundles are kept small through code
splitting and tree shaking, images are served in modern formats at appropriate sizes through
the media service and a content delivery network, and third-party scripts are scrutinised
because each one is a tax on every page. The teams run performance tests in continuous
integration that fail the build if a change regresses a key metric beyond its budget.
Internationalisation is built in from the start, with all user-facing text externalised for
translation and with layouts that adapt to right-to-left languages and longer translated
strings.


# Mobile Engineering

The company ships native mobile applications for merchants to manage their stores on the go.
The applications are built with a shared business-logic core and platform-native user
interfaces, balancing code reuse against a first-class feel on each platform. Mobile releases
follow the app stores' review processes, so the teams maintain a careful release train with
feature flags that let them enable capabilities without shipping a new binary. Because mobile
clients run on devices the company does not control, the applications are defensive about
connectivity, caching data for offline use and reconciling changes when the device reconnects.


# Machine Learning Platform

Machine learning powers search ranking, recommendations, fraud detection, and merchant churn
prediction. The machine learning platform provides a feature store that serves consistent
features to both training and serving, so that a model sees the same data distribution in
production as it did in training, avoiding the training-serving skew that silently degrades
model quality. Models are trained in reproducible pipelines, versioned alongside the data and
code that produced them, and evaluated against held-out data and fairness checks before
promotion. Models are served behind the same kind of API as any other service, with monitoring
that watches not only latency and errors but also prediction distributions, so that a model
whose inputs drift away from its training distribution is detected and retrained.


# Operational Runbooks

# People, Hiring, and Ways of Working

The company's engineering culture is as deliberately designed as its systems. The following
sections describe how the company hires, onboards, and supports its engineers, and the everyday
norms that keep collaboration healthy. These policies exist to make the company a place where
good engineers do their best work and stay.


## Hiring and the Interview Process

The company hires for capability and trajectory rather than for a checklist of technologies,
because tools change but the ability to learn and to reason endures. The interview process is
structured and consistent so that candidates are evaluated fairly and so that interviewer bias
is reduced. A typical loop includes a conversation about past work, a practical coding exercise
that resembles real work rather than abstract puzzles, a system design discussion calibrated to
the candidate's level, and a values conversation. Interviewers write detailed, evidence-based
feedback and a clear recommendation, and a hiring committee reviews the packet to make the
final decision, which keeps any single interviewer from dominating the outcome. Candidates are
given the same exercises within a level so that comparisons are like for like.


## Onboarding

New engineers are productive quickly because onboarding is treated as an engineering problem
with a defined outcome. In the first week a new engineer sets up their environment using
automated scripts, reads the relevant portions of this handbook, and ships a small, real change
to production with the support of an onboarding buddy. In the first month they take part in
their team's on-call rotation in a shadow capacity, learning the systems by observing how they
fail and recover. Each new hire has a written thirty-, sixty-, and ninety-day plan with
concrete milestones, and their manager checks in frequently to remove obstacles. The company
measures time to first commit and time to first on-call shift and works to shorten both without
sacrificing depth.


## Code of Conduct and Collaboration Norms

The company expects everyone to treat colleagues with respect and to assume good intent.
Disagreement is welcome and even encouraged, because better decisions come from surfacing and
resolving genuine differences, but disagreement is about ideas and is expressed without
personal attacks. Meetings have agendas and end with clear decisions and owners. Written
communication is favoured for anything that others may need to reference later, and important
decisions are recorded in durable documents rather than lost in chat. Engineers are expected to
make their work visible, to ask for help early rather than struggle silently, and to give help
generously when asked.


## Leave, Benefits, and Flexible Work

The company offers a generous paid-time-off policy and expects people to use it, because rested
engineers make better decisions and sustainable pace is a long-term advantage. Parental leave
is provided to all new parents regardless of gender, and the company supports a gradual return
to work. The company operates a flexible, hybrid working model in which teams agree on the days
they gather in person for collaboration and reserve other days for focused individual work.
Compensation is reviewed regularly against market benchmarks, and the company is transparent
with engineers about how levels and pay bands work so that growth is predictable rather than
mysterious.


## Career Growth and Performance

The company maintains parallel career tracks for individual contributors and for managers, so
that an engineer who wishes to deepen their technical impact is not forced into management to
advance. Each level has a written description of the scope, autonomy, and impact expected, and
promotion is a recognition that an engineer is already operating at the next level rather than
a bet that they will grow into it. Performance is evaluated against these expectations with
evidence gathered from peers, and feedback is delivered continuously rather than saved for an
annual surprise. Managers are expected to coach, to remove obstacles, and to advocate for their
people, and they are evaluated on the health and growth of their teams.


# Product Management

Product managers at the company are responsible for the why and the what, while engineering
owns the how. A product manager develops a deep understanding of merchant problems through
research and data, frames those problems clearly, and works with engineering and design to
decide what to build. The company prioritises ruthlessly, because the cost of building the
wrong thing is not just the wasted effort but the opportunity forgone. Every significant
initiative starts with a written brief that states the problem, the target customer, the
measurable outcome, and the hypotheses being tested, and ends with an honest assessment of
whether the outcome was achieved.

The company ships in small increments and learns from real usage rather than betting on big
launches. Features are released behind flags to progressively larger cohorts, and their impact
is measured against the outcome defined in the brief. When a feature does not move its metric,
the company is willing to remove it, because unused features carry a permanent maintenance cost
and clutter the product. Product, engineering, and design operate as a single team with shared
goals rather than as a relay race in which requirements are thrown over a wall.


# Customer Support Operations

Customer support is the company's direct line to merchant reality and is treated as a source of
insight, not merely a cost. Support agents have tools that give them the context to resolve
issues quickly while respecting strict access controls, so that helping a merchant never means
unfettered access to sensitive data. Issues that reveal product defects or recurring confusion
are routed back to the relevant engineering and product teams through a structured feedback
loop, and the volume and themes of support contacts are reviewed regularly to find systemic
fixes. The company sets clear response-time targets by severity and measures satisfaction so
that support quality is visible and improvable.


# Finance Engineering and Procurement

Because the platform moves money, financial correctness is a first-class engineering concern.
The settlement and reconciliation systems ensure that every authorisation, capture, refund,
fee, and payout is accounted for and that the company's ledger agrees with the processors'
records to the cent. Discrepancies are surfaced automatically and investigated promptly,
because small unexplained differences often signal a real defect. Cloud spending is treated
with the same rigour as any other cost: teams see the cost of the infrastructure they operate,
expensive resources are tagged to their owners, and the company reviews spending trends to
eliminate waste without compromising reliability.


# Legal, Contracts, and Vendor Management

Engineering decisions frequently have legal and contractual implications, and the company
brings legal expertise into those decisions early rather than as a final gate. When a team
adopts a third-party service, it reviews the vendor's security posture, data-handling
practices, and contractual commitments, because the company remains accountable to its
merchants for the behaviour of its suppliers. Open-source software is used widely and its
licences are tracked so that the company honours their terms. Data-processing agreements are in
place with every vendor that handles personal data on the company's behalf, and the company
maintains a register of these relationships to support its privacy obligations.


# Disaster Recovery and Business Continuity

The company plans for disasters that go beyond the failure of a single component, such as the
loss of an entire region or the corruption of a critical dataset. Data is backed up
continuously, backups are encrypted, and crucially the company regularly tests that backups can
actually be restored, because an untested backup is only a hope. The platform's multi-region
design means that the loss of a region degrades capacity but does not stop the business, as
traffic fails over to the remaining regions. The company runs disaster-recovery exercises on a
schedule, deliberately failing components to confirm that the documented procedures work and
that the recovery objectives are met in practice rather than only on paper.


# Networking and Edge

Traffic from shoppers and merchants enters the platform through a global edge network that
terminates encryption close to the user, absorbs distributed denial-of-service attacks, and
caches static content. Behind the edge, a layer of load balancers distributes requests to
healthy service instances, and a service mesh handles service-to-service communication with
mutual authentication, retries, and fine-grained traffic control. Network policy is defined as
code and follows a default-deny posture, so that a service can talk only to the dependencies it
has been explicitly permitted to reach, which limits the blast radius of a compromised
component.


# Performance Engineering

Performance is a feature that the company designs for rather than hopes for. Teams set explicit
latency and throughput targets for their services and validate them with load tests that
reproduce realistic traffic patterns, including the spiky bursts that accompany flash sales and
marketing campaigns. Engineers profile hot paths to find the few places where time is actually
spent, because intuition about performance is frequently wrong. Caching is applied deliberately
at the layers where it pays off, with careful attention to invalidation, because a stale cache
can be worse than no cache. The company treats a latency regression as a defect to be fixed,
not as an inevitability to be tolerated.


# Glossary

This glossary defines terms used throughout the handbook so that newcomers can read any section
without prior context.

Idempotency key: a unique value a client attaches to a mutating request so the server can
detect and ignore duplicate retries, returning the original result.

Error budget: the small amount of unreliability a service level objective permits, used to
balance feature velocity against reliability work.

Canary deployment: a release technique in which a new version serves a small fraction of
traffic and is automatically compared against the old version before full rollout.

Blue-green deployment: a release technique that runs a new fleet alongside the current one and
shifts traffic over, enabling instant rollback.

Circuit breaker: a pattern that stops sending requests to a failing dependency for a time,
allowing it to recover and preventing cascading failure.

Bulkhead: an isolation pattern that partitions resources so that a failure in one area cannot
exhaust resources needed elsewhere.

Expand-and-contract: a schema migration pattern that adds new structure, migrates consumers,
and only then removes old structure, avoiding downtime.

Service level objective: a target for a service level indicator over a window, expressing the
reliability the team commits to.

Golden signals: the four key metrics of latency, traffic, errors, and saturation that summarise
a service's health.

Dead-letter queue: a holding area for messages that repeatedly fail processing, so they do not
block the main queue.

Feature flag: a runtime switch that enables or disables a capability without deploying new
code, decoupling deployment from release.

Tokenisation: replacing a sensitive value such as a card number with a non-sensitive reference,
keeping the raw value out of scope.

Trunk-based development: a branching model in which engineers integrate small changes into the
main branch frequently behind flags.

Distributed tracing: a technique that follows a single request across services, recording the
time spent in each span.

Medallion architecture: a data lake design with bronze, silver, and gold layers representing
raw, cleaned, and aggregated data.

Training-serving skew: a degradation in model quality caused by differences between the data
seen during training and during serving.

Least privilege: the principle of granting each identity the minimum permissions required to
perform its function.

Recovery point objective: the maximum amount of data, measured in time, that an organisation is
willing to lose in a disaster.

Recovery time objective: the maximum acceptable duration to restore service after a disaster.

Toil: manual, repetitive operational work that scales with system size and is a target for
automation.

Saga: a way to coordinate a multi-service workflow as a sequence of local transactions, each
with a compensating action that undoes it on failure.

Outbox pattern: writing an event to a database table in the same transaction as a state change
so the event can be published reliably afterwards.

Backpressure: a mechanism by which a slow consumer signals upstream to slow a fast producer,
preventing unbounded queues.

Load shedding: deliberately dropping the least important work when a service approaches
saturation, to protect its core function.

Admission control: limiting how much concurrent work a service accepts so that it never takes
on more than it can serve.

Sharding: partitioning data across multiple stores by a key so that load and storage spread
evenly as the system grows.

Hot partition: a shard that receives a disproportionate share of traffic, becoming a bottleneck
while others are idle.

Cache stampede: a surge of identical recomputations when a popular cache entry expires and many
requests miss at once.

Single-flight: coalescing concurrent identical requests so that only one does the work and the
rest share its result.

Anti-corruption layer: an adapter that translates between an external system's model and the
internal domain, isolating the latter.

Strangler fig: a migration strategy that grows new functionality around a legacy system until
the old one can be removed.

Service mesh: an infrastructure layer that handles service-to-service communication with mutual
authentication, retries, and traffic control.

Mutual authentication: a scheme in which both parties to a connection verify each other's
identity, not just the client verifying the server.

Default-deny: a security posture in which all access is forbidden unless explicitly permitted.

Canary analysis: the automated comparison of a new version against the current one on key
metrics during a gradual rollout.

Guardrail metric: a metric watched during a rollout that, if it regresses beyond tolerance,
automatically halts or reverses the change.

Contract test: a test that verifies a service honours the API contract its consumers depend on,
catching breaking changes early.

Correlation identifier: a value attached to all the work done for a single request so it can be
traced across services in logs.

Data lineage: a record of where each dataset and column comes from and how it was transformed,
supporting trust and debugging.

Feature store: a system that serves consistent machine-learning features to both training and
serving to avoid skew.

Blast radius: the extent of the damage a failure or change can cause, which engineers work to
minimise.

Chaos experiment: a deliberate, controlled injection of failure used to verify that a system
degrades gracefully.

Runbook: a documented procedure for diagnosing and resolving a specific operational situation.


# Security Controls Catalogue

The company maintains a catalogue of the security controls that protect the platform and its
customers' data. Each control states what it protects against and how it is implemented and

## Control: Multi-factor authentication

The Multi-factor authentication control protects against credential theft and account takeover.

security team providing standards, tooling, and review for high-risk changes.

# Design Patterns and Engineering Practices

The platform relies on a recurring set of patterns to solve common distributed-systems problems
consistently. Engineers are expected to recognise these patterns and apply them rather than
reinventing solutions. Each entry below states the problem the pattern solves, how it works,
and when to use it.


## Pattern: Retry with exponential backoff and jitter

This pattern addresses transient failures in remote calls that would succeed if tried again. It
works as follows: the caller retries a failed request after waiting an interval that grows
exponentially and is randomised to avoid synchronised retries. Use it for any idempotent remote
call, but never for non-idempotent operations without an idempotency key. The company applies
this pattern consistently so that engineers encounter familiar solutions across services, and
its use is expected wherever the underlying problem appears. Applying a known pattern well is
strongly preferred over inventing a bespoke mechanism that the next engineer will have to
decipher.


## Pattern: Circuit breaker

This pattern addresses a failing dependency that would otherwise consume the caller's resources
and cascade. It works as follows: the caller tracks failures and, past a threshold, stops
calling the dependency for a cool-down period before cautiously probing again. Use it for any
dependency whose failure could exhaust threads, connections, or memory in the caller. The
company applies this pattern consistently so that engineers encounter familiar solutions across
services, and its use is expected wherever the underlying problem appears. Applying a known
pattern well is strongly preferred over inventing a bespoke mechanism that the next engineer
will have to decipher.


## Pattern: Bulkhead isolation

This pattern addresses one overloaded code path starving unrelated work of shared resources. It
works as follows: resources such as thread pools and connection pools are partitioned so each
workload has its own bounded allocation. Use it for services that serve a mix of critical and
non-critical traffic from shared resources. The company applies this pattern consistently so
that engineers encounter familiar solutions across services, and its use is expected wherever
the underlying problem appears. Applying a known pattern well is strongly preferred over
inventing a bespoke mechanism that the next engineer will have to decipher.


## Pattern: Outbox pattern

This pattern addresses the need to update a database and publish an event atomically without
distributed transactions. It works as follows: the event is written to an outbox table in the
same transaction as the state change, and a relay publishes it afterwards. Use it for any
service that must reliably emit an event whenever it changes state. The company applies this
pattern consistently so that engineers encounter familiar solutions across services, and its
use is expected wherever the underlying problem appears. Applying a known pattern well is
strongly preferred over inventing a bespoke mechanism that the next engineer will have to
decipher.


## Pattern: Saga for distributed workflows

This pattern addresses a business process spanning multiple services that cannot share a single
transaction. It works as follows: the process is modelled as a sequence of local transactions,
each with a compensating action that undoes it if a later step fails. Use it for long-running
workflows such as order fulfilment that touch several services. The company applies this
pattern consistently so that engineers encounter familiar solutions across services, and its
use is expected wherever the underlying problem appears. Applying a known pattern well is
strongly preferred over inventing a bespoke mechanism that the next engineer will have to
decipher.


## Pattern: Command-query responsibility segregation

This pattern addresses a single model struggling to serve both complex writes and high-volume
reads. It works as follows: the write model and read model are separated, with the read model
kept up to date from events emitted by the write side. Use it for domains with very different
read and write shapes or volumes. The company applies this pattern consistently so that
engineers encounter familiar solutions across services, and its use is expected wherever the
underlying problem appears. Applying a known pattern well is strongly preferred over inventing
a bespoke mechanism that the next engineer will have to decipher.


## Pattern: Idempotent consumer

This pattern addresses at-least-once message delivery causing duplicate processing. It works as
follows: the consumer records the identifiers of processed messages and ignores duplicates,
making repeated delivery harmless. Use it for every consumer of an at-least-once message
stream. The company applies this pattern consistently so that engineers encounter familiar
solutions across services, and its use is expected wherever the underlying problem appears.
Applying a known pattern well is strongly preferred over inventing a bespoke mechanism that the
next engineer will have to decipher.


## Pattern: Cache-aside with single-flight

This pattern addresses expensive reads and cache stampedes when a hot entry expires. It works
as follows: the application reads through a cache and, on a miss, coalesces concurrent
recomputations so only one populates the cache. Use it for read-heavy paths with a small set of
very popular keys. The company applies this pattern consistently so that engineers encounter
familiar solutions across services, and its use is expected wherever the underlying problem
appears. Applying a known pattern well is strongly preferred over inventing a bespoke mechanism
that the next engineer will have to decipher.


## Pattern: Rate limiting and load shedding

This pattern addresses a surge of traffic threatening to overwhelm a service. It works as
follows: the service caps the rate per client and sheds the least important work first when it
approaches saturation. Use it for any service exposed to untrusted or bursty traffic. The
company applies this pattern consistently so that engineers encounter familiar solutions across
services, and its use is expected wherever the underlying problem appears. Applying a known

will have to decipher.


## Pattern: Backpressure

This pattern addresses a fast producer overwhelming a slower consumer. It works as follows: the
consumer signals its capacity upstream so the producer slows down rather than building an
unbounded queue. Use it for streaming and pipeline stages with mismatched throughput. The
company applies this pattern consistently so that engineers encounter familiar solutions across
services, and its use is expected wherever the underlying problem appears. Applying a known
pattern well is strongly preferred over inventing a bespoke mechanism that the next engineer
will have to decipher.


## Pattern: Feature flagging

This pattern addresses the risk of coupling code deployment to feature release. It works as
follows: capabilities are gated behind runtime flags so they can be enabled gradually and

## Pattern: Strangler fig migration

This pattern addresses replacing a legacy component without a risky big-bang rewrite. It works

## Pattern: Anti-corruption layer

This pattern addresses an external system's model leaking into and distorting the internal

## Pattern: Sharding by tenant

This pattern addresses a dataset too large or too hot for a single partition. It works as

## Pattern: Dead-letter queue

This pattern addresses a malformed message blocking a consumer indefinitely. It works as

pattern consistently so that engineers encounter familiar solutions across services, and its

## Pattern: Graceful degradation

This pattern addresses the failure of a non-essential dependency taking down core

optional enhancements layered on a core function. The company applies this pattern consistently

# Architecture Decision Records

The company records significant architectural decisions as short, durable documents so that
future engineers understand not just what was decided but why, and what alternatives were
weighed. The summaries below capture decisions that shape the platform today. Each remains in
force unless explicitly superseded by a later record.


## Decision Record 1: Adopt postgresql as the default database

Context: teams were choosing databases inconsistently, raising operational cost. The company
decided to adopt PostgreSQL as the default database. The alternatives considered were a managed
key-value store or a document database for everything. The decision was made because PostgreSQL
is reliable, transactional, richly featured, and well understood, and a single default reduces
the operational surface that the company must master. The consequence is that teams across the
platform follow this approach by default, the tooling and standards reinforce it, and any
departure must be justified and approved at architecture review. This record remains in force
and is revisited only if the conditions that motivated it change materially.


## Decision Record 2: Use a service-per-database pattern with no shared tables

Context: a shared database had coupled teams and made independent deployment risky. The company
decided to use a service-per-database pattern with no shared tables. The alternatives
considered were a single shared schema with access conventions, or a data-access service in
front of one database. The decision was made because giving each service its own database
preserves team autonomy and prevents the hidden coupling that a shared schema inevitably
creates. The consequence is that teams across the platform follow this approach by default, the
tooling and standards reinforce it, and any departure must be justified and approved at
architecture review. This record remains in force and is revisited only if the conditions that
motivated it change materially.


## Decision Record 3: Standardise on blue-green deployment with canary analysis

Context: in-place deployments made rollbacks slow and risky. The company decided to standardise
on blue-green deployment with canary analysis. The alternatives considered were rolling updates
in place, or recreate deployments with a maintenance window. The decision was made because
running a new fleet alongside the old enables instant rollback and lets automated canary
analysis catch regressions before full exposure. The consequence is that teams across the
platform follow this approach by default, the tooling and standards reinforce it, and any

## Decision Record 4: Communicate state changes through an event bus

Context: point-to-point synchronous calls created tight coupling and fragile chains. The

were synchronous orchestration through a central coordinator, or direct database integration.
The decision was made because publishing domain events lets producers and consumers evolve

# Frequently Asked Questions

This section answers questions that engineers, especially newcomers, ask most often. The
answers reflect current practice and are kept in sync with the rest of the handbook.

Question: How do I deploy a change to production? Answer: Merge your reviewed pull request into
the main branch; the continuous integration pipeline builds and tests it, and the continuous
delivery pipeline promotes it through staging and a canary before the full fleet, halting
automatically if any guardrail metric regresses.

Question: What do I do first when I am paged? Answer: Acknowledge the page, open the service
dashboard to assess customer impact, check for a recent deployment that correlates with the
regression, and mitigate by the fastest safe means, which is usually a rollback or a traffic
failover, before investigating the root cause.

Question: How do I add a new configuration value? Answer: Define it in the configuration
service rather than hard-coding it, give it a safe default, and read it through the
configuration client so it can be changed at runtime without a deployment.

Question: When should I introduce a new datastore or language? Answer: Only when an existing
tool genuinely cannot meet the need; you must document the capability gap, estimate the multi-
year operational cost, find at least two owners, and obtain approval at architecture review.

Question: How do I make an operation safe to retry? Answer: Have the client send an idempotency
key and have the server record that key with the result, so a repeated request returns the
original outcome instead of performing the work twice.

Question: How are secrets handled? Answer: Secrets live in the secrets manager, are injected at
runtime, are never committed to source control or baked into images, and are rotated every
ninety days; a leaked secret is an incident and is rotated immediately.

Question: What is the rule for breaking API changes? Answer: Do not make them within a version;
changes must be additive, and a genuinely breaking change requires a new version that runs
alongside the old one until all clients migrate.

Question: How do I run a database migration safely? Answer: Use the expand-and-contract pattern
so the schema supports old and new shapes at once, migrate consumers, and only then remove the
old shape; never lock a large table for more than a second.

Question: What should my service emit for observability? Answer: The four golden signals on a
dashboard, structured logs with a correlation identifier on every request, and distributed
traces, with alerts defined on customer-visible symptoms.

Question: How much test coverage is required? Answer: Changed lines need at least eighty
percent branch coverage, but coverage is a floor, not a goal; favour a large base of fast unit
tests, fewer integration tests, and only a thin layer of end-to-end tests.

Question: How do I request access to a production system? Answer: Request the specific role you
need through the access management workflow; access is least-privilege and time-bound, and
every grant and use is logged for audit.

Question: What happens after an incident? Answer: The team writes a blameless postmortem
documenting the timeline, contributing factors, impact, and concrete action items with owners
and due dates, which are tracked to completion.

Question: How do feature flags relate to deployment? Answer: They decouple deployment from
release; code can be deployed dark and then enabled gradually for specific cohorts, and a
problematic feature can be disabled instantly without a rollback.

Question: How do I handle personal data? Answer: Collect only what you need, classify it by
sensitivity, restrict and audit access to sensitive classes, honour data subject rights, and
retain it only as long as necessary.

Question: What is the error budget and how does it affect me? Answer: It is the small amount of
unreliability your service level objective permits; when you have budget you can ship quickly,
and when it is exhausted you pause risky changes and focus on reliability.

Question: How do I choose between synchronous and asynchronous communication? Answer: Use a
synchronous call when the caller needs an immediate answer and can tolerate the dependency's
latency, and use asynchronous events when you want producers and consumers to evolve
independently and survive each other's downtime.

Question: What should I do before deleting a service? Answer: Confirm from telemetry that no
traffic or dependencies remain, migrate any consumers, archive its data per the retention
policy, remove its infrastructure as code, and update the service catalogue.

Question: How do I keep a cache from causing problems? Answer: Set sensible expiries, guard
against stampedes with single-flight coalescing or early refresh, plan for invalidation
explicitly, and ensure the system degrades gracefully when the cache is briefly unavailable.

Question: When should I write a design document? Answer: Write one for any non-trivial change,
anything that crosses team boundaries, and anything that introduces new infrastructure; it
should state the problem, the proposed solution, the alternatives, the impact, and the
operational plan.

Question: How do I handle a third-party dependency that is down? Answer: Apply a timeout and a
circuit breaker so it cannot exhaust your resources, degrade gracefully by continuing with
reduced capability, and fail over to a secondary provider if one exists.

Question: What is the expectation for documentation? Answer: Leave the documentation better
than you found it; keep your service's catalogue entry, runbooks, and design notes current,
because they are written for the next person who has to operate or change the system.

Question: How do I make sure my change can be rolled back? Answer: Keep changes small and
reversible, make schema changes with expand-and-contract, hide new behaviour behind a feature
flag, and confirm the previous version can serve traffic before you rely on the new one.

Question: What do I do if I am unsure whether something is a security issue? Answer: Treat it
as one until proven otherwise; raise it with the security team, avoid discussing details in
public channels, and never test a suspected vulnerability against production without
coordination.


# Document Control and Maintenance

This handbook is a living document and the canonical reference for engineering and operations
at Veltrix Systems. Each section has an owning team that is responsible for keeping it
accurate, and any change to a documented standard must go through the architecture review
process before it takes effect. The handbook is versioned alongside the rest of the company's
documentation, and significant changes are announced to the engineering organisation so that
everyone works from the same current practice rather than from memory or folklore.

When you find something in this handbook that is wrong, out of date, or unclear, you are
expected to fix it rather than work around it, because the next person who reads it will be
better served by your correction. Treat the handbook the way you treat code: review changes,
keep it consistent, and improve it incrementally. A standard that is documented but not
followed is worse than no standard at all, so where practice and documentation diverge, raise
the discrepancy and resolve it deliberately, updating either the practice or the document so
that the two agree. The strength of Veltrix Systems's engineering culture rests on the shared,
current understanding that this handbook is meant to capture.
